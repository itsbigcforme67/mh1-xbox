# Two tool fixes: cov_report_g.py and text_map.py (4 Nov 2026)

Research agent, low-CPU round. Changed: tools/cov_report_g.py, tools/text_map.py; regenerated by text_map.py
docs/text_coverage.md and docs/survey/mhg_text_untranslated.txt; two own lines added to text/mhg_en_own.tsv with
tools/text_own.py. No build, no game run. Not committed.

## 1. tools/cov_report_g.py

### What was wrong

- **gcc local labels counted as functions.** `nm -n -l` lists `.L1234` labels (one per jump-table case, loop heads) as
  `t` symbols with a source line. The tool put them in the per-file list of function starts, so a function's body
  ended at its first case label and any G code further down was not seen. Today's G binary has 7959 such labels
  (of 13521 `t/T/w/W` symbols).
- **G changes through macros not seen.** Many G ports switch behaviour through a macro defined in a `VERSION_MHG`
  block above the function (em_area_move_init's `G_AM`, enemy_mv's `EMU_KIND_27`, Pl_damage_sub's `PB`, pl_mv071's
  `PL_MV071_*`). The body itself has no G marker, so the tool called it MH1.
- Found while fixing those two:
  - **The body ran past the function's end** (up to the next function's start line), so a `#ifdef VERSION_MHG` that
    belongs to the next function counted for this one. Six names were called G only because of that
    (Set_equip_data, char_make_init, Disp_back, disp_pachinger, Info_control, em_hungry_ck: in each the marker is
    after the closing brace).
  - **`#elif defined(VERSION_MHG)` read as the MH1 branch.** The common pattern
    `#if defined(VERSION_MHG) && defined(__MWERKS__)` / `#elif defined(VERSION_MHG)` / `#else` flipped a single flag
    at every `#elif`/`#else`, so the PC's G code in the `#elif` branch counted as MH1 (set04_m, set04_trans).
  - **`#if ... && !defined(VERSION_MHG)` read as a G branch** (only a leading `!` was recognised): sort_sub and
    omake_check, which are MH1-only and not built for G, were counted as G.

### What changed

- Names starting with `.L` are skipped everywhere (symbol map, function starts, the zero-table pass, which already
  skipped them).
- A body ends at the first line starting with `}` (the closing brace in column 0) or the next function, whichever
  comes first.
- The `#if` walk keeps, per open `#if`, whether the current branch is G, MH1-only, and what earlier branches tested;
  `#elif` takes its own condition, `#else` is G only after a negative test (`#ifndef` / `!defined`) and MH1 only after
  a positive one.
- A function counts as G when its body uses a macro `#define`d inside an `#if` on VERSION_MHG (either branch) in its
  own file; the count is printed. Macros defined that way in headers (CW_OFS, LBSHOP_OFS, IBO, ...) do not count as G:
  the G-CHANGED list marks those rows `H` in a new `hdr` column and the heading says how many (usually layout only).
- New mode `--names LIST`: runs the same test on the G-CHANGED rows of an earlier report (or a plain name list)
  instead of a coverage dump, so an old coverage run can be re-checked against today's code without a COV=1
  rebuild. Static functions gcc inlined away are looked up in the source file the report names; names that are not
  in the binary and whose source is gone or MH1-only are counted apart.

945 G-CHANGED names of docs/survey/mhg_cov_g.txt were re-checked with `--names` against today's G binary

|---|---:|---:|---:|

## 2. tools/text_map.py: lobby 0x638430 / 0x638480

### What was wrong

The G "save complete" and "deletion complete" dialogs of the Multi Matching BB login (lobby 0x638430 / 0x638480) had
three stray bytes each as *official* English. The step that made them is the **US -> MH1 JP table-index pairing**
(run_us, step 2 in the tool's header): the MH1 JP table `bs_strtbl_mmbb_dialog` (lobby) was found in the US lobby by a
code reference, but the US build dropped the MMBB dialogs (a Japanese ISP service), so the last three rows' pointers
lead into other data in the US lobby (US 0x690EC0 / 0x690EF0 / 0x690F10). `good_english` accepted the bytes: not
empty, not Japanese, same printf conversions. The MH1 table got them at lobby 0x650550 / 0x650640 / 0x650690, and G's
two twins took them over through the "identical text" step (G's 0x650550 twin was edited, so it did not).

### What changed

`good_english` (used for every US, manual and Freedom pair) now also refuses a candidate that is **not text**: the
Japanese has three or more kana / kanji, and the English has no run of two letters or digits (ASCII, or full-width as
in the US memory-card names). New drop reason "not text".

### Before / after

- `text_map.py` re-run (with `--report docs/text_coverage.md --ids docs/survey/mhg_text_untranslated.txt`). The only
  changes in the tables: MH1 loses lobby 0x650550 / 0x650640 / 0x650690 (US: 6852 -> 6849 JP strings with English,
  dropped "not text" 3), G loses lobby 0x638430 / 0x638480 as official. Nothing else changed in either table (diffed
  against a run of the old code on the same inputs). A first version of the rule also caught two real US lines
  written in full-width letters (main 0x384258 / 0x3842A8, memory-card names); full-width letters now count.
- No official pair exists: the US has no MMBB dialogs and Freedom has nothing in these slots (TM_KEYS trace:
  Freedom None). So both got our own lines (text/mhg_en_own.tsv, flags `-`, layout as the Japanese: three blank
  lines, the message, three blank lines, the button line): "Save complete." / "Deletion complete." with
  "Press the ○ button.". text_own.py: 2 lines checked, 0 to look at. text_own.py appended them under a new copy of the
  "Multi Matching BB login and NET file screens (lobby)" heading at the end of the file; they could be moved up beside
  lobby 0x638340 by hand.
- docs/text_coverage.md, G total: official 11761 -> 11759, ours 1170 -> 1172, with English unchanged (12931). The
  untranslated list now shows both ids as "ours".
- Not checked on screen (no game run): that the dialog draws the English lines where the Japanese ones were.
